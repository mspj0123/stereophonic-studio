# ブラウザ内分離のメモリ最適化 テスト結果

**実施日**: 2026-08-17
**対象**: ブランチ `feature/memory-streaming`
**テスト設計**: `docs/test_design/メモリ最適化テスト設計.md`
**環境**: ローカル配信（`python3 -m http.server 8765`）／ Chrome（claude-in-chrome で操作）／
`crossOriginIsolated: true` ／ CPU(WASM)・4スレッド ／ テスト機は WebGPU 非対応（`requestAdapter()` が null）

---

## 1. 総括

| 区分 | 実施 | 合格 | 未実施 |
|---|---|---|---|
| 正常系 (N) | 10 | 10 | 0 |
| 異常系 (E) | 9 | 9 | 1（E-3） |
| 回帰 (R) | 2 | 2 | 1（R-3） |

**最重要の結果は N-4**：改修前後の出力を全サンプル比較して**差がゼロ**。音質への影響がないことを
実測で確認した。目的だったメモリは **436.8MB → 41.3MB** に減少。

## 2. 正常系

### N-1 分離が最後まで通る ✅

| 実行 | モデル | 所要時間 |
|---|---|---|
| 1回目（初回・モデルDLあり） | ダウンロード 172MB | 1分26秒 |
| 2回目以降（キャッシュから） | Cache API | 0分39〜41秒 |

25秒の曲に対し、モデルのキャッシュが効くと**約半分の時間**で完了するようになった。

### N-2 パートの表示順 ✅
`vocals / drums / bass / other` の順で従来どおり追加された。

### N-3 チャンクの連続性 ✅

Worker が送出したチャンク（25秒＝1,102,500サンプルの曲）：

```
offset=      0, length=257985
offset= 257985, length=257985
offset= 515970, length=257985
offset= 773955, length=257985
offset=1031940, length= 70560
                --------------
                計 1,102,500 サンプル ＝ 25秒 × 44100Hz
```

隙間・重複なし。合計が全長と完全に一致。

### N-4 出力波形の同一性 ✅ **（最重要）**

同一入力に対し、旧実装（`main` の `processor.js`）と新実装（ストリーミング）で分離し、
4トラック×2ch×1,102,500サンプル ＝ **8,820,000サンプルを全比較**。

| トラック | 最大絶対差 | 差のあったサンプル数 | 相対RMS誤差 |
|---|---|---|---|
| drums | **0** | **0** | 0 |
| bass | **0** | **0** | 0 |
| other | **0** | **0** | 0 |
| vocals | **0** | **0** | 0 |

**完全に同一**（ビット単位で一致）。ストリーミング化による音質の変化はない。

### N-5 出力が無音でない ✅

| トラック | RMS |
|---|---|
| drums | 0.03916 |
| bass | 0.05168 |
| other | 0.10651 |
| vocals | 0.00502 |

すべて 0 より大きい。vocals が小さいのはテスト音源が合成音で、声に相当する成分が
Demucs の学習分布から外れているため（実楽曲では通常もっと大きくなる）。

### N-6 分離の妥当性 ✅

| 項目 | 値 |
|---|---|
| 元音声の RMS | 0.1342 |
| 4トラック合計の RMS | 0.13161 |
| 相対誤差 | **5.12%** |

Demucs は「4トラックの合計 ≒ 原音」になる性質があり、それが保たれている。
チャンクの取りこぼしや二重加算があればこの誤差は大きく崩れる。

### N-7 継ぎ目に段差がない ✅

チャンク境界の「隣接サンプルの差」を、境界でない位置500点の分布と比較した（値は周辺平均との比）。

| トラック | 境界4か所の値 | 通常位置の中央値 | 通常位置の95% | 通常位置の最大 |
|---|---|---|---|---|
| drums | 0.36 / 0.13 / 0.01 / 0.01 | 0.42 | 3.01 | 8.31 |
| bass | 1.35 / 1.40 / 1.41 / 0.79 | 0.92 | 2.07 | 3.97 |
| other | 0.79 / 3.76 / 0.33 / 3.59 | 0.75 | 2.75 | 4.24 |
| vocals | 0.04 / 0.67 / 0.67 / 0.12 | 0.77 | 2.37 | 5.90 |

**すべての境界値が、境界でない位置の最大値を下回っている**＝境界は統計的に特別ではない。
（N-4 の完全一致と合わせ、継ぎ目の問題は無いと判断できる）

### N-8 モデルのキャッシュ ✅
2回目の分離で `cachehit` が通知され、`download` フェーズが1回も発生しなかった。

### N-9 メモリ削減 ✅ **（本改修の目的）**

120秒の曲を分離しながら `performance.measureUserAgentSpecificMemory()` でサンプリング。

| 実装 | 測定値の推移(MB) | **ピーク** |
|---|---|---|
| 旧 | 41.3 → 161 → 172.1 → **436.8** → 41.3 → 41.3 → 41.3 | **436.8MB** |
| 新 | 41.3 → 41.3 → 41.3 → 41.3 | **41.3MB** |

旧実装では、モデル受信（161〜172MB）→ 出力バッファ確保（436.8MB）と段階的に跳ね上がるのが
はっきり観測できた。新実装ではこの跳ね上がりが消え、**約90%減**。

> **この測定の限界（正直な注記）**：この API は1回の測定に約13秒かかるため、新実装では
> 4点しかサンプリングできていない。モデル読み込み時の一時的な山（172MB前後）を
> 捉え損ねている可能性がある。したがって「新実装のピークが常に41.3MB」とまでは言えない。
> 確実に言えるのは、**曲の長さに比例して増えていた出力バッファぶん（この条件で約190MB）と、
> モデル受信の二重確保ぶん（172MB）が無くなった**こと。

### N-10 UIが固まらない ✅
分離中の経過時間表示：`0:05 → 0:08 → 0:12 → 0:16 → 0:20 → 0:24 → 0:28 → 0:32`（3秒間隔で取得）。
滑らかに進んでおり、メインスレッドが応答し続けている。

## 3. 異常系

| No | 内容 | 結果 | 実際の挙動 |
|---|---|---|---|
| E-1 | 10分超の曲 | ✅ | 「曲が長い（約10.5分）ため…10分以内の曲でお試しください」で開始前に中止 |
| E-2 | 低メモリ端末で6分の曲 | ✅ | `deviceMemory=4` を偽装したところ上限が5分に切り替わり、6分の曲を中止 |
| E-3 | 低メモリ端末の警告表示 | ⚠ 未実施 | 起動時に一度だけ評価される箇所で、偽装のタイミングを作れなかった。コード上は E-2 と同じ判定を使用 |
| E-4 | 音声でないファイル | ✅ | 「この音声ファイルを読み込めませんでした。対応していない形式か…」／ボタンは操作可能に復帰 |
| E-5 | Cache API が使えない | ✅ | `caches` を参照すると例外が出る状態でも、素の fetch にフォールバックしてモデル読込に成功 |
| E-6 | キャッシュ保存の失敗 | ✅ | `cache.put` が失敗しても `Model cache failed (ignored)` とログを残して続行、読込は成功 |
| E-7 | モデルURLが不正 | ✅ | 「分離モデルの取得に失敗しました (HTTP 404)」 |
| E-8 | Content-Length が無い | ✅ | `arrayBuffer()` フォールバックで読込に成功 |
| E-9 | Worker からのエラー | ✅ | E-7 の経路で Worker→UI へエラーが伝わることを確認（UI表示は E-4 で確認） |
| E-10 | 連続実行 | ✅ | 2回目も正常完了（0:39）。状態は残らない |

### E-4 に伴う改善
テキストファイルを選んだとき、改修前は「分離に失敗しました: Unable to decode audio data
（…メモリ不足の可能性…）」と**原因を誤解させる案内**が出ていた。
原因がはっきりしているエラーには専用メッセージを出すよう修正した。

## 4. 回帰確認

| No | 内容 | 結果 | 備考 |
|---|---|---|---|
| R-1 | 3D再生 | ✅ | 再生位置が 0:23 まで進行、立体音響トグルON、3D配置パッドに各パートが表示 |

### 波形描画について
テスト音源では波形が薄く表示される。キャンバスのピクセルを解析したところ
**描画自体は行われており**（点灯36px・縦方向の広がり7px／キャンバス高60px）、
合成音のため振幅が小さいことが原因と確認した。描画コードは今回一切変更しておらず、
入力する AudioBuffer は N-4 のとおり旧実装とビット単位で同一のため、回帰ではない。

## 6. 未確認事項（ユーザー側での確認が必要）

| 項目 | 理由 |
|---|---|
| **WebGPU 経路** | テスト機にGPUが無く検証不能。GPU利用は既定オフのオプトインだが、ONにする場合は実機確認が必要 |
| **スマホ実機** | 実機が無い。今回の削減でスマホでの成功率は上がるはずだが、実測はできていない |
| **実楽曲での聴感** | 権利の都合でテスト配置できない。N-4 で波形の同一性は保証されているため、改修による音質劣化は無い |
| **長い曲（5〜10分）の実走** | 新上限まで実際に流す試験は時間の都合で未実施。E-1/E-2 でガードの動作は確認済み |
