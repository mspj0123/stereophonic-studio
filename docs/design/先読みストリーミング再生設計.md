# 先読みストリーミング再生 設計書

- **作成日:** 2026-09-14
- **対象:** `stream.html`（新規ページ。既存の `index.html` / `player.html` には一切手を入れない）
- **ブランチ:** `feature/streaming-playback`

---

## 1. 目的

現在は「分離が**全部**終わってから再生」になっている。4分の曲なら、分離が終わるまで
何も聴けない。これを **分離しながら、追いついた分から立体音響で鳴らす** 形にする。

利用者から見た変化は1点だけ。

```
現在:  [────────── 分離（数分）──────────] → 再生開始
新規:  [先読み] → 再生開始（分離は裏で走り続ける）
        ↑ ここまでの待ち時間を、端末の性能に応じて自動で決める
```

---

## 2. 前提と物理的な制約

### 2.1 消せない遅延：7.8秒

`htdemucs` は**非因果モデル**である。`TRAINING_SAMPLES = 343980`（44.1kHz で **7.80秒**）の
セグメントを丸ごと見てから出力するため、**ある瞬間の音を分離するには「その後の音」が要る**。

- これは計算速度とは無関係で、**GPUをどれだけ速くしても消えない**
- 本ページの用途（ライブラリの曲を頭から聴く）では「再生開始までの待ち」に化けるだけなので許容する
- **マイク入力など低遅延用途には転用できない。** 因果モデルへの差し替えが必要になる

### 2.2 分離速度 R（実測が必要な唯一の値）

R = 分離にかかる秒数 ÷ 音声の秒数。**R < 1 なら実時間より速い。**

| 実測環境 | R |
|---|---|
| Chrome / CPU(WASM) 4スレッド / WebGPU非対応機（2026-08-17） | **約1.6**（25秒の曲に39〜41秒） |
| WebGPU | **未計測**（テスト機にGPUが無く未検証） |

---

## 3. 中心となる考え方：R > 1 でも成立させる

「実時間より速くないとストリーミング再生はできない」というのは**誤り**である。
必要なのは「**再生が終わる前に分離が終わること**」だけで、それは先読み量で買える。

曲長を L、分離済みの長さを d、分離速度を R とする。いま再生を始めると：

```
再生が終わる時刻      = 現在 + (L − 0)          … 先頭から L 秒かかる
分離が終わる時刻      = 現在 + (L − d) × R      … 残り (L−d) 秒ぶんを R 倍の速さで
```

追い抜かれない条件は `L ≥ (L − d) × R` であり、整理すると

> **d ≥ L × (1 − 1/R)**

| R | L=4分(240秒) のとき必要な先読み d | 再生開始までの実時間 |
|---|---|---|
| 0.5（GPUで2倍速） | 0秒（最初のチャンクだけでよい） | **約8秒** |
| 1.0（等速） | 0秒 | **約8秒** |
| 1.6（現状のCPU実測） | 90秒 | **約144秒** |
| 2.0 | 120秒 | 240秒 |

**R=1.6 の現状でも、4分の曲なら 144秒で鳴り始める。** 全部終わるのを待つ 384秒に比べて
**4分早い。** つまり **GPUが無くても価値がある。** GPUがあれば約8秒になる。

### 3.1 安全率

R は曲の途中で変動する（他タブの負荷、サーマルスロットリング）。実測 R をそのまま使うと
ぎりぎりで破綻するため、次のようにする。

```js
const R_SAFE = R_measured * 1.15;            // 15%悪化しても耐える
const need   = L * (1 - 1 / R_SAFE);
const lead   = Math.max(need, MIN_LEAD_SEC); // MIN_LEAD_SEC = 12秒（チャンク2つ分）
```

- R は**最初の2チャンクを実測してから**決める（固定値を置かない。§CLAUDE.md「実測せずに見積もらない」）
- 以後もチャンクが届くたびに移動平均で更新し、悪化したら**自動で一時停止して貯め直す**

### 3.2 それでも足りなかったとき（スタベーション）

再生位置がバッファの先端に追いつく場合がある。**音を途切れさせるより止める。**

- `audioCtx.suspend()` で全体を止める。**スケジュール済みの時刻がずれない**のが利点
- 画面に「バッファ中」と出し、`lead` 秒ぶん貯まったら `resume()`
- 3回以上スタベーションしたら、以後の `lead` を1.5倍に増やす（学習）

## 4. 構成

### 4.1 ファイル

| ファイル | 扱い |
|---|---|
| `stream.html` | **新規**。本機能のすべて |
| `separator-worker.js` | **そのまま再利用（無改変）** |
| `vendor/demucs-web/*` | **そのまま再利用（無改変）** |
| `coi-serviceworker.js` | **そのまま再利用（無改変）** |
| `index.html` / `player.html` | **触らない** |

既存の Worker は 2026-08-17 のメモリ最適化で
`post({type:'chunk', offset, length, tracks})` を**確定分から順に送る**作りになっている。
本機能はこの出力をそのまま使うため、**Worker 側の改造は不要**。

### 4.2 データの流れ

```
ファイル選択
  ↓ decodeAudioData
Float32Array(L,R)
  ↓ postMessage('separate')           ← 既存Workerをそのまま使う
Worker: meta → chunk × N → done
  ↓ 'chunk' {offset, length, tracks{drums,bass,other,vocals}}
チャンクキュー（パートごと）
  ↓ 先読み量に達したら再生開始
AudioBufferSourceNode を絶対時刻で予約
  ↓
[パートごとの固定ノード鎖] → masterGain → destination
```

### 4.3 パートごとのノード鎖（既存 `index.html` と同じ構成）

チャンクごとに作り直すのは **`AudioBufferSourceNode` だけ**。
パンナー以降は曲の間ずっと使い回す（作り直すと定位が飛ぶ）。

```
[chunk source] ─┐
[chunk source] ─┼→ volumeGain ─┬→ directGain ──────────────→ masterGain
[chunk source] ─┘              └→ panner → airLPF → threeDGain → masterGain
```

- `PannerNode` は `panningModel:'HRTF'`, `distanceModel:'inverse'`,
  `refDistance:1.5`, `maxDistance:20`, `rolloffFactor:0.5` … 既存と同じ値
- 既定の配置（聴取者を原点、前方が −Z）

  | パート | x | y | z | 位置 |
  |---|---|---|---|---|
  | vocals | 0 | 0 | −2 | 正面 |
  | drums | 0 | 1 | 2 | 後方やや上 |
  | bass | −2 | 0 | 0 | 左 |
  | other | 2 | 0 | 0 | 右 |

### 4.4 チャンクの予約

Worker のチャンクは**連続かつ重なりなし**で届く（2026-08-17 の実測：
offset 0 / 257985 / 515970 …、各 length 257985 = 5.85秒）。したがって
受け取った順にそのまま並べればよい。**こちら側でオーバーラップ加算はしない。**

```js
const when = playStartTime + offset / sampleRate;   // audioCtx の絶対時刻
src.start(when);
```

- `playStartTime` は再生開始時に一度だけ決める
- 一時停止は `audioCtx.suspend()`。`currentTime` が進まないので**予約時刻を直さなくてよい**
- すでに時刻を過ぎているチャンクは捨てる（到着が遅れた場合の保険）

## 5. 異常系

| 事象 | 対処 |
|---|---|
| 分離が再生に追いつかない | `suspend()` して貯め直す。3回目からは先読み量を1.5倍 |
| WebGPU の初期化に失敗 | 既存と同じくCPU(WASM)へ自動で落とす。R を測り直す |
| Worker が `error` を返す | 再生を止め、理由を画面に出す。既存ページには影響しない |
| `crossOriginIsolated` が false | スレッドが使えず R が悪化する。警告を出したうえで続行 |
| 曲が長すぎる（メモリ） | 分離済みチャンクは**再生後に解放**する。全長ぶんは保持しない |
| ファイルが音声でない | `decodeAudioData` の失敗を捕捉して案内を出す |
| 再生中にタブが非表示 | `audioCtx` は動き続ける。Worker も動く。何もしない |

### 5.1 メモリ

既存ページは分離結果を全長ぶん `AudioBuffer` に持つ。本ページは**流して捨てる**。

- 再生済みのチャンクは `onended` で参照を切る
- 未再生のチャンクだけを保持 → 保持量は先読み量に比例（R=1.6・4分で最大90秒ぶん ≒ 4パート×90秒×2ch×4byte ≒ **127MB**）
- R が大きいほどメモリを食う。**先読みが 120秒を超える場合は警告**を出す

---

## 6. この設計で「やらない」こと

- **既存ページへのリンク追加をしない。** `index.html` を1文字も変えない方針のため、
  `stream.html` へは直接URLで入る。導線は別途の判断とする
- **分離結果の保存をしない。** 保存が要るなら既存ページを使う。本ページは再生に集中する
- **3Dの編集UIを作らない。** 定位は固定プリセット＋ON/OFFのみ。
  既存ページの編集機能と重複させない
- **因果モデルへの差し替えをしない。** §2.1 のとおり別問題
