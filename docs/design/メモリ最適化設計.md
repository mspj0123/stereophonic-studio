# ブラウザ内分離のメモリ最適化 設計書

**対象**: `d-browser-app`（GitHub Pages で公開しているブラウザ内音源分離アプリ）
**作成日**: 2026-08-17
**背景**: 分離中に「アプリが終了しました」「ページが応答しません」でタブ／ブラウザが落ちる問題が
継続していた。Web Worker 化（2026-07-21）でUIの固まりは解消したが、**メモリ不足によるクラッシュ**は
残っていたため、根本原因であるメモリの持ち方そのものを作り直す。

---

## 1. 改修前の問題：曲の全長ぶんを何重にも保持していた

4分の曲（44.1kHz・約1,058万サンプル。ステレオ1本＝約85MB）を分離したときの内訳。

| 場所 | 内訳 | 量 |
|---|---|---|
| Worker | 入力 L/R | 85MB |
| Worker | 出力4トラック×2ch（`outputs`） | **339MB** |
| Worker | 重み配列（`weights`） | 42MB |
| Worker | モデル受信時の二重確保（`chunks[]` ＋ `combined`） | **344MB** |
| Worker | ONNXセッション＋推論中の中間テンソル | 200MB〜 |
| メイン | 元の AudioBuffer | 85MB |
| メイン | Worker から受け取った `tracks` | **339MB** |
| メイン | それをコピーして作った AudioBuffer 4本 | **339MB** |
| | **合計ピーク** | **約1.5〜1.8GB** |

太字の3か所が「持たなくてよいのに持っていた」ぶん。とくに出力バッファは**曲が長くなるほど
線形に増える**ため、長い曲・低メモリ端末から順に落ちていた。

対症療法として入口を「6分まで／低メモリ端末は3分まで」と狭めていたが、構造は変えていなかった。

---

## 2. 改修の3本柱

### ① 分離結果を「確定した部分から順に吐き出す」（ストリーミング化）

`vendor/demucs-web/processor.js` の `separate()`。

Demucs は 7.8秒（`TRAINING_SAMPLES` = 343,980サンプル）のセグメントを 75% ずつずらしながら
重ね合わせる。この構造上、サンプル位置 `p` に寄与するのは

```
start <= p < start + TRAINING_SAMPLES
```

を満たすセグメントだけなので、**セグメント `start` の処理が終わった時点で `p < start + stride`
の範囲は値が確定している**（`stride` = 257,985サンプル ≒ 5.85秒）。

```
セグメント0  [====== 7.8秒 ======]
セグメント1        [====== 7.8秒 ======]
セグメント2              [====== 7.8秒 ======]
             ↑確定  ↑確定
             ここまで吐き出してメモリを解放できる
```

そこで、全長ぶんの配列をやめ、**`TRAINING_SAMPLES` 分だけのスライディングバッファ**を使い回す：

1. セグメントを処理してバッファに加算する
2. 確定した `stride` 分を重みで割って `onChunk()` で呼び出し元へ渡す
3. 未確定ぶんをバッファ先頭へ詰め直し、空いた末尾をゼロで埋める

**重ね合わせの計算式そのものは一切変えていない**ため、出力波形は改修前と完全に同一になる
（テストで全サンプル一致を確認済み。`docs/test_results/` 参照）。

- Worker側の出力保持量は **曲の長さに依存しない固定値**（4トラック×2ch＋重み＝約11MB）になる。
- `onChunk` を渡さずに呼ぶと従来どおり全体をまとめて返す互換モードで動く（内部実装は共通）。

あわせて、セグメントごとの推論結果テンソルを使い終えた時点で `dispose()` するようにした
（とくに WebGPU 使用時の GPU バッファ解放）。

### ② モデル受信バッファの二重確保をなくす

改修前は受信チャンクを配列に貯めてから別配列へコピーしていたため、172MB のモデルで
一時的に約344MB を占有していた。`Content-Length` は取得できているので、**先に必要量を確保して
直接書き込む**方式に変更（`_readWithProgress()`）。

`Content-Length` と実サイズが食い違う場合（圧縮転送など）に備え、足りなくなったら拡張する
保険を入れてある。長さが取れない場合は従来どおり `arrayBuffer()` にフォールバックする。

### ③ モデルを Cache API に保存する

改修前は毎回 172MB の取得をブラウザのHTTPキャッシュ任せにしていた。`caches` に明示的に保存し、
2回目以降はダウンロードなしで即座に読み込む（`_fetchModel()`）。

- キャッシュ名は `constants.js` の `MODEL_CACHE_NAME`。**モデルを差し替えたら版数を上げること**。
- `caches` が使えない環境（`file://` など非セキュアコンテキスト）では自動的に素の fetch に戻る。
- 206 Partial Content は Cache API に保存できない仕様のため、`200` のときだけ保存する。
- 容量不足などで保存に失敗しても、**処理そのものは続行する**（キャッシュはあくまで高速化）。

### ④ メインスレッド側の二重確保をなくす（①に伴う変更）

`player.html`。Worker が全体をまとめて返さなくなったので、

1. Worker から先に `meta`（全長）を受け取り、**出力先の AudioBuffer を先に作る**
2. `chunk` が届くたび `copyToChannel()` で直接書き込む

とした。これで「受け取った Float32Array」と「AudioBuffer」を二重に持つ必要がなくなる。
元の AudioBuffer も L/R を取り出した直後に参照を切って解放させる。

## 3. 改修後のメモリ（4分の曲）

| 場所 | 内訳 | 量 |
|---|---|---|
| Worker | 入力 L/R | 85MB |
| Worker | スライディングバッファ（曲長に依存しない） | 約11MB |
| Worker | モデル受信 | 172MB |
| Worker | ONNXセッション＋中間テンソル | 200MB〜 |
| メイン | 出力 AudioBuffer 4本 | 339MB |
| | **合計ピーク** | **約600MB** |

**残る最大の項目（339MB）は再生用の AudioBuffer** で、3D再生する以上どうしても必要になる。
1分あたり約85MB 増えるため、曲の長さの制限は完全には外せない。

そのため上限は **10分（メモリの少ない端末は5分）** に緩和した（従来 6分／3分）。

## 4. 異常系の設計

| シナリオ | 対処 |
|---|---|
| モデルのダウンロード失敗（HTTPエラー） | `_fetchModel()` で HTTP ステータスを見て日本語メッセージで throw。UIに表示 |
| `Content-Length` が無い／実サイズと食い違う | 長さ無し→`arrayBuffer()` にフォールバック。食い違い→バッファを拡張 |
| Cache API が使えない | `caches` の参照・`open`・`match` をすべて try/catch。失敗したら素の fetch で続行 |
| キャッシュ保存の失敗（容量不足など） | try/catch で握りつぶして続行（機能に影響しない） |
| 206 Partial Content が返る | 保存をスキップ（Cache API の仕様上保存不可） |
| 出力先 AudioBuffer 未作成のまま chunk 到着 | `player.html` 側で内部エラーとして reject し、UIにエラー表示 |
| チャンク書き込み中の例外 | onMessage 全体を try/catch し、Promise を reject してリスナーを外す |
| 曲が長すぎる | デコード直後に長さを判定して、上限（10分／5分）を超えたら開始前に中止 |
| WebGPU で失敗 | Worker を terminate → 再デコード → CPU(WASM) でやり直し（従来どおり） |
| メモリ不足によるタブ/ブラウザのクラッシュ | JS では捕捉不可。UIに事前の案内（他タブを閉じる・短い曲・PC推奨）を表示 |
